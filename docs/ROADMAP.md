# Roadmap: от MR-дашборда к personal engineering cockpit

Статус: **план согласован по приоритетам** (2026-09-08), вопросы 3–8 отложены на конец. Реализация не начата.

### Решения после обсуждения
- **Быстрое ревью остаётся** как отдельный режим: быстрее и дешевле по токенам. Для него resolver ищет
  свой project-local skill (`mr-review-quick`, переопределяется `SKILL_REVIEW_QUICK`), при отсутствии — агент
  полного ревью с промптом «быстрый проход». Название и tooltip делаем понятными: «Быстрое ревью · только diff, экономит токены».
- **Каждое действие — через skill проекта** (реализовано 2026-09-09, см. `docs/SKILLS.md`): dashboard — это интерфейс
  поверх агентов проекта, а не свой ревьюер. Карта «действие → ожидаемое имя skill» фиксирована в коде
  (`internal/skill.Actions`), показывается в doctor/UI, пользователь описывает skills в проекте сам. Правило для
  новых действий (Phase 5–7: разбор бага, CI, исправление выбранных замечаний): сначала добавить строку в карту.
- **«Мои MR» = где я автор.** Роль `author` добавляется в синхронизацию по умолчанию (`GITLAB_SYNC_ROLES=reviewer,assignee,author`).
- **Новые приоритеты** (поднимаются вперёд остальных фаз): адаптивный «энтерпрайз» дизайн и **понимание контекста сессии**
  (в каком чате идёт операция: новый пустой контекст или продолжение существующей сессии, и чем этот контекст уже заполнен).
- Вопросы 3–8 (§4) остаются открытыми; соответствующие задачи (bug mode, правки чужих MR, отставание от develop,
  stream-json прогресс, порядок релизов) сдвигаются в конец плана.
Источник: UX-спецификация «Cockpit» (40 пунктов), сопоставленная с текущей версией 0.2.1.

Легенда размеров: **S** до половины дня · **M** день · **L** 2–3 дня. Зависимости указаны стрелкой `←`.

## 1. Решения по спорным пунктам спецификации (предложение)

| Пункт | Решение | Почему |
|---|---|---|
| «Быстрое ревью» | **Убрать из основной строки**, оставить в overflow как «Быстрое ревью (только diff)» либо удалить совсем — см. вопрос 1 | спецификация запрещает кнопку без пояснения объекта; при этом дешёвый режим полезен при лимитах токенов |
| «Проверить» как действие MR | **Заменить на «Проверить изменения»** = один запуск: diff `last_reviewed_sha..head` + пересопоставление прежних findings (new / still present / resolved / obsolete) | это и есть текущий verify, дополненный ревью новых коммитов |
| «Проверить замечание» | Отдельный мини-запуск по одному finding, результат: подтверждено / ложное / неактуально / недостаточно данных | п.14 |
| Open terminal / Open IDE в Workspaces | **Не делать.** Из браузера нельзя безопасно открыть терминал/IDE. Вместо этого «Скопировать путь» и «Показать diff» | нет безопасного механизма |
| Статус Paused у workspace | **Не вводить**: у worktree нет такого состояния. Статусы: активная сессия / есть незакоммиченное / чисто / запушено | лишняя сущность |
| «Обновить ветку» (behind develop) | **Только показывать** отставание; rebase не делать — см. вопрос 6 | запись в ветку пользователя |
| Merge, approvals, обсуждения | Оставить GitLab, давать ссылку «GitLab ↗» | п.37 |
| Keyboard UX (п.21) | Отложить в самый конец; минимум `/` поиск и `?` подсказка | не влияет на понятность |
| Mobile (п.33) | Не делать; только «не ломается на узком окне» | п.33 |
| Вопросы агента «в процессе» | Агент в неинтерактивном режиме не может спросить посреди работы. Реализуем так: агент **останавливается** и возвращает структурированный список вопросов → сессия в состоянии «Нужен ваш ответ» → ответ отправляется **в ту же сессию** (resume) и работа продолжается | ограничение `claude -p`; поведение для пользователя совпадает со спецификацией |
| Bug mode (п.8) | Не отдельная кнопка, а режим «Исследовать»: авто-определение по меткам/названию (bug, fix, ошибка) с переключателем в форме — см. вопрос 3 | меньше кнопок в строке |
| Fix findings на чужих MR | По умолчанию только свои MR (push в чужую ветку недопустим). Для чужих — режим «предложить патч» без push — см. вопрос 5 | безопасность |
| Fake progress % | Не показываем. Фазы + elapsed | п.29 |

## 2. Модель состояний (контракт для UI)

**MR / AI review:** `never` → «Ещё не проверен» · `running` → «Проверяется» · `current` → «Проверен» (+N открытых) · `stale` → «Есть новые изменения (+N коммитов)» · `failed` → «Ошибка».
**MR / GitLab:** pipeline ✓/✕/●, approvals n/m, unresolved threads, отставание от target, draft, merged/closed.
**Задача:** `new` → «Новая» · `researching` → «Исследуется» · `ready_to_implement` → «Есть план» · `implementing` → «Пишется код» · `testing` → «Запускаются тесты» · `reviewing` → «Self-review» · `waiting_for_user` → «Нужен ваш ответ» · `ready` → «Готово к MR» · `failed` → «Ошибка» · `done` → «MR создан».
**Сессия (run):** `queued` → «В очереди» · `running` → «Выполняется» (+фаза) · `waiting_for_user` → «Нужен ваш ответ» · `done` → «Завершена» · `failed` → «Ошибка» · `cancelled` → «Отменена».
**Finding:** `open` → «Нужно проверить» · `confirmed` → «Подтверждено» · `false_positive` → «Ложное срабатывание» · `resolved` → «Исправлено» · `obsolete` → «Больше не актуально» · `ignored` → «Игнорируется» · `unclear` → «Недостаточно данных».

Внутренние enum'ы в UI не показываются (п.24).

## 6. Как продолжить работу с другой машины

Всё нужное лежит в этом репозитории; локальные `data/`, `logs/`, `runtime/`, `.env` не нужны.

```sh
cd ~/projects                      # рядом должен быть чекаут основного проекта (tradernet) с его .claude/
git clone git@github.com:arturgilmanov94/gitlab_manager.git mr-review
cd mr-review
go build -o mr-review ./cmd/mr-review && go test ./...     # Go 1.22+ (или взять бинарник из Releases)
./mr-review doctor && ./mr-review
```

Состояние на 2026-09-09: выпущена **0.7.0** (после 0.6.0 добавлены История MR с автоочисткой списка, читаемые адреса
`/-/review/12`, вердикт из замечаний). До этого — **0.6.0**. Закрыты фазы 0, 1, D, P; из Phase C — продолжение сессии для «Проверить
изменения» и цепочка сессий на странице запуска; из Phase 2 — данные GitLab на MR, markdown и ссылки «Код ↗»,
ручные статусы замечаний; Phase 3 — Обзор; из Phase 4 — страница «Сессии» и текущий шаг агента; Phase 8 — Workspaces.
Осталось из UI-фаз: выбор «продолжить сессию» перед запуском (C), инкрементальное ревью и `verify_finding` (2),
структурные этапы вместо «последнего вызова» и «Нужен ваш ответ» по существу (4), Phase 5–7.
**Следующий шаг — Phase C** (контекст сессии), затем Phase 2 (MR как эталон: данные GitLab, инкрементальное ревью, findings-карточки).

Локальная машина: `go` не в PATH по умолчанию — `export PATH=$HOME/.local/go/bin:$PATH`; системный git 2.25.

Соглашения: контракт кнопок — `docs/UX_ACTIONS.md`, изменения UI сверяются с ним; каждая фаза = запись в
`CHANGELOG.md` + bump `VERSION` + тег `vX.Y.Z` → GitHub Actions собирает релиз; тесты `go test ./...` зелёные
перед пушем; dashboard не меняет файлы основного проекта и не хранит credentials.

Чтобы продолжить с AI-ассистентом, достаточно открыть репозиторий и сказать: «прочитай docs/ROADMAP.md и начинай Phase C».

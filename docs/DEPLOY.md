# Развернуть у себя

Пошаговое руководство: от чистой машины до работающего dashboard на вашем проекте. Рассчитано на то, что
вы делаете это **впервые** и про сам инструмент ничего не знаете. Если под рукой есть coding-агент
(Claude Code, Codex, Cursor) — в конце есть [готовые промпты](#разворачиваю-с-помощью-нейронки), которые
делают шаги 1–6 за вас.

Итог: локальный веб-интерфейс на `http://127.0.0.1:8765`, который запускает агентов **вашего** проекта
(его `CLAUDE.md`, агентов и skills) на ваши MR и задачи в GitLab. Ничего не публикуется наружу: только ваша
машина, ваш уже авторизованный `glab` и ваша подписка на агента.

## Шаг 0 — что нужно на машине

| Нужно | Зачем | Проверка |
|---|---|---|
| Linux x86-64, `git` | бинарник собран под эту платформу | `uname -m` → `x86_64` |
| Рабочая копия вашего проекта | агент работает в нём и читает его правила | каталог с `.git` |
| [`glab`](https://gitlab.com/gitlab-org/cli) | весь доступ к GitLab идёт через него | `glab version` |
| Хотя бы один агент: [Claude Code](https://docs.claude.com/en/docs/claude-code) (`claude`), Codex (`codex`) или Cursor (`cursor-agent`) | кто, собственно, работает | `claude --version` |
| Go (версия из `go.mod`, сейчас 1.25+) | **только** если собираете из исходников | `go version` |

Токены GitLab и агента вводить в dashboard не нужно и негде: он пользуется теми, что уже есть у `glab` и у
агента на этой машине.

> **Агент установлен через nvm/fnm/volta?** Начиная с 0.26.0 dashboard находит его и при запуске из меню
> приложений. На более старых версиях агент был виден только при запуске из терминала.

## Шаг 1 — поставить бинарник

**Вариант A — готовый архив (проще).** Возьмите `mr-review-<version>-linux-amd64.tar.gz` из
[Releases](https://github.com/arturgilmanov94/gitlab_manager/releases) и распакуйте **рядом** с рабочей
копией проекта:

```sh
cd ~/projects                                   # здесь лежит ваш проект, например ~/projects/myapp
tar -xzf ~/Downloads/mr-review-0.27.0-linux-amd64.tar.gz
cd mr-review
```

Проверить целостность (необязательно): `sha256sum -c mr-review-0.27.0-linux-amd64.tar.gz.sha256`.

**Вариант B — собрать из исходников.**

```sh
git clone https://github.com/arturgilmanov94/gitlab_manager.git
cd gitlab_manager
go build -ldflags "-X main.version=$(cat VERSION)" -o mr-review ./cmd/mr-review
```

Зависимость всего одна (`modernc.org/sqlite`, чистый Go) — ни cgo, ни Python, ни venv.

## Шаг 2 — авторизоваться

```sh
glab auth login --hostname gitlab.example.com   # ваш GitLab; для gitlab.com хост тот же
claude                                          # войти в аккаунт и выйти из сессии
```

`glab` должен быть авторизован **на том хосте, где лежит ваш проект**. Проверка:
`glab auth status` и `glab api user` — второе должно вернуть ваш профиль.

## Шаг 3 — показать, где проект

Если dashboard распакован рядом с проектом (`~/projects/mr-review` и `~/projects/myapp`) — он найдёт проект
сам. Иначе пропишите путь явно:

```sh
echo 'PROJECT_ROOT=/home/me/projects/myapp' >> .env
```

Каталог проекта должен быть git-репозиторием с настроенным `origin` на GitLab: из remote берутся хост и путь
проекта. Если рядом лежит несколько репозиториев с `.claude/`, автоопределение честно скажет
`Several sibling git repositories` — тогда `PROJECT_ROOT` обязателен.

## Шаг 4 — параметры `.env`

`.env` лежит **рядом с бинарником** (шаблон со всеми переменными и комментариями — `.env.example`,
его можно просто скопировать: `cp .env.example .env`). Переменные окружения перекрывают файл, относительные
пути считаются от каталога бинарника.

**Минимум, который работает у большинства** — пустой `.env` или три строки:

```sh
PROJECT_ROOT=../myapp
BASE_BRANCH=main        # от какой ветки создавать ветки задач; ПО УМОЛЧАНИЮ develop
REPORT_LANGUAGE=ru      # язык текстов агента: ru | en | de | uk | kk
```

> `BASE_BRANCH=develop` — самая частая правка: если в проекте основная ветка `main`, поменяйте, иначе ветки
> задач будут создаваться от несуществующей `develop`.

**Что стоит прописать под свой проект:**

| Переменная | Прописать, если | Пример |
|---|---|---|
| `BASE_BRANCH` | основная ветка не `develop` | `main` |
| `GITLAB_HOST`, `GITLAB_PROJECT` | `origin` нестандартный и хост/путь не разобрались | `gitlab.example.com`, `group/sub/myapp` |
| `GITLAB_ISSUE_PROJECTS` | задачи ведутся в отдельных проектах-трекерах; пусто = все проекты, где вы assignee | `group/tracker,group/sub/myapp` |
| `GITLAB_SYNC_ROLES` | нужны не все роли в MR | `reviewer,assignee` |
| `GITLAB_SYNC_ONLY_PROJECT` | нужны MR из всех проектов, а не только текущего | `0` |
| `HIGHLIGHT_LABELS` | свои метки приоритета (цвета: red, orange, yellow, green, blue, gray) | `blocker:red,bug:orange,feature:green` |
| `DEFAULT_RUNNER`, `CLAUDE_MODELS` | основной агент не `claude` или нужен свой список моделей | `codex`, `default,opus,sonnet` |
| `PORT` | 8765 занят | `8766` |
| `RUN_CONCURRENCY` | сколько агентов работают одновременно (по разным MR/задачам) | `2` |
| `RUN_TIMEOUT_SEC`, `CLAUDE_MAX_BUDGET_USD` | нужен потолок по времени/деньгам на запуск | `2700`, `5` |
| `REVIEW_WORKTREE_TTL_MIN` | проект большой и жалко диск (или наоборот — не удалять) | `30`, `0` |
| `CLAUDE_EXTRA_ALLOWED_TOOLS` | ревью должно уметь звать линтер/анализатор | `Bash(php *) Bash(composer *)` |
| `SKILL_*` | ваши skills называются иначе, чем ожидает dashboard (см. [шаг 6](#шаг-6--skills-проекта)) | `SKILL_REVIEW_FULL=code-review` |
| `TERMINAL_CMD` | «Продолжить в терминале» не находит эмулятор | `gnome-terminal --working-directory={dir} -- bash -lc {cmd}` |

Полная таблица всех переменных — в [README](../README.md#настройки), построчные комментарии — в `.env.example`.

## Шаг 5 — проверить и запустить

```sh
./mr-review doctor     # что найдено, что нет; exit code 1 при FAIL
./mr-review            # сервер + браузер: http://127.0.0.1:8765
```

Читать `doctor` так:

- **OK** — всё нашлось.
- **WARN** — можно работать. `Skill: … not found` означает, что действие пойдёт по `CLAUDE.md` проекта и
  промпту dashboard, а не по вашему skill (см. шаг 6). `Agent: codex WARN` — просто нет этого агента.
- **FAIL** — работать нельзя, надо чинить: не найден проект, `glab` не авторизован, нет ни одного агента.

Другие способы запуска:

```sh
./mr-review serve      # foreground, без браузера
./mr-review start      # в фоне (pid в runtime/server.pid, лог в logs/server.log)
./mr-review stop | status
./install-desktop.sh                # ярлык «MR Review» в меню и на рабочем столе (только в архиве релиза)
./install-desktop.sh --no-desktop   # то же, но без ярлыка на рабочем столе
./install-desktop.sh --uninstall    # убрать ярлыки и иконку
```

## Шаг 6 — skills проекта

Это главное, ради чего инструмент существует: он **не приносит своего ревьюера**, а запускает агентов и skills
вашего проекта из `.claude/`. Работать он будет и без них (по `CLAUDE.md` + промпт dashboard), но «как ваш
ревьюер» — только когда в проекте есть файл с ожидаемым именем.

| Действие в интерфейсе | Ожидаемое имя | Переменная | Насколько нужно |
|---|---|---|---|
| Запустить ревью | `mr-review` | `SKILL_REVIEW_FULL` | **самое полезное, начните с него** |
| Быстрое ревью | `mr-review-quick` | `SKILL_REVIEW_QUICK` | необязательно (возьмёт полное ревью) |
| Проверить изменения | `mr-review-verify` | `SKILL_REVIEW_VERIFY` | необязательно (возьмёт полное ревью) |
| Проверить замечание | `mr-verify-finding` | `SKILL_VERIFY_FINDING` | необязательно |
| Исследовать задачу | `task-plan` | `SKILL_PLAN` | полезно |
| Решить задачу | `task-implement` | `SKILL_IMPLEMENT` | полезно |
| Исправить замечания ревьюеров | `mr-fix-comments` | `SKILL_FIX_COMMENTS` | полезно |
| Исправить выбранные замечания | `mr-fix-findings` | `SKILL_FIX_FINDINGS` | необязательно |
| Разобрать / исправить CI | `mr-ci-analyze`, `mr-ci-fix` | `SKILL_CI_ANALYZE`, `SKILL_CI_FIX` | необязательно |
| Проверить на стенде | `mr-stand-test` | `SKILL_STAND_TEST` | только если есть стенд |

Файл кладётся в проект (не в dashboard) одним из трёх способов — что найдётся раньше, то и победит:

1. `.claude/agents/<имя>.md` — запустится как `claude --agent <имя>` (во frontmatter обязателен `name:`);
2. `.claude/commands/**/<имя>.md` — вызовется как `/<имя> <ссылка>`;
3. `.claude/skills/<имя>/SKILL.md` — так же, как `/<имя> <ссылка>`.

Если ваши skills уже называются иначе — ничего не переименовывайте, пропишите имена в `.env`
(`SKILL_REVIEW_FULL=code-review`) или выберите их в интерфейсе на странице «Проверка окружения», там же есть
выпадающий список найденных skills.

**Готовый минимум — скопируйте в свой проект и поправьте под стек.**

`.claude/skills/mr-review/SKILL.md`:

```markdown
---
name: mr-review
description: Ревью merge request по правилам проекта — находит реальные проблемы с файлом, строкой и фиксом.
---

Ты ревьюишь merge request этого репозитория. Ссылка, ветки и head SHA приходят в промпте.

1. Прочитай MR и его diff: `glab mr diff <iid>`, обсуждения — `glab api projects/:id/merge_requests/<iid>/discussions` (только GET).
2. Изучи затронутый код вокруг правки: как эту задачу решают в проекте, что ещё зависит от изменённого.
3. Проверь: корректность и краевые случаи, безопасность (ввод пользователя, права, секреты), запросы к БД
   и производительность, обработку ошибок, тесты, соответствие правилам из CLAUDE.md.
4. Каждое замечание — с файлом, строкой и конкретным предложением фикса. Severity: CRITICAL, HIGH, MEDIUM, LOW, INFO.
   Не придирайся к стилю, который проходит линтер проекта.
5. Ничего не меняй: только чтение. Ответ — строго JSON по схеме, которую даёт dashboard.
```

`.claude/skills/task-plan/SKILL.md`:

```markdown
---
name: task-plan
description: Исследование задачи GitLab перед реализацией — план, файлы, риски, вопросы.
---

Ты исследуешь задачу GitLab в этом репозитории. Ссылка и описание задачи приходят в промпте.

1. Прочитай задачу; при необходимости подтяни связанные issue/MR через `glab api` (только GET).
2. Найди затронутые модули и разберись, как в проекте принято решать такие задачи.
3. Составь план: шаги, файлы и что в них меняется, риски и регрессии, открытые вопросы, оценка размера.
4. Если без решения человека продолжать нельзя — заполни `ask` вопросами и оставь остальные поля минимальными.
5. Код не меняй. Ответ — строго JSON по схеме, которую даёт dashboard.
```

`.claude/skills/task-implement/SKILL.md`:

```markdown
---
name: task-implement
description: Реализация задачи GitLab в отдельном workspace по правилам проекта.
---

Ты решаешь задачу GitLab в этом репозитории. Ты уже находишься в git worktree на своей ветке.

1. Разберись в задаче и в существующем коде; следуй правилам из CLAUDE.md и соглашениям проекта.
2. Внеси правки только в этом workspace. Не делай commit, push, checkout, reset — это сделает разработчик кнопками.
3. Прогони тесты и линтеры проекта по затронутому коду; что не удалось проверить — вынеси в `todo`.
4. Перечитай собственный дифф перед ответом. Предложи текст коммита по соглашению проекта.
5. Ответ — строго JSON по схеме, которую даёт dashboard.
```

Подробный контракт каждого действия — что именно dashboard кладёт в промпт и какие поля разбирает обратно —
в [docs/SKILLS.md](SKILLS.md). JSON-схему ответа dashboard передаёт агенту сам, придумывать её не нужно.

## Разворачиваю с помощью нейронки

Два независимых промпта. Первый — агенту **в каталоге, куда ставите dashboard**:

```text
Разверни локальный dashboard mr-review из github.com/arturgilmanov94/gitlab_manager по его docs/DEPLOY.md.
Сделай по шагам и покажи результат каждого:
1. Проверь предпосылки: linux x86-64, git, glab (авторизован ли — `glab auth status`), наличие claude / codex /
   cursor-agent, go нужной версии если будешь собирать из исходников.
2. Поставь бинарник: возьми последний релизный архив, либо склонируй репозиторий и собери
   `go build -ldflags "-X main.version=$(cat VERSION)" -o mr-review ./cmd/mr-review`.
3. Создай .env из .env.example и заполни под мой проект: PROJECT_ROOT — путь к моей рабочей копии,
   BASE_BRANCH — основная ветка моего проекта (проверь по origin/HEAD, не угадывай), REPORT_LANGUAGE.
   Остальное оставь по умолчанию, пока не понадобится.
4. Запусти `./mr-review doctor`, разбери каждую строку FAIL и почини. WARN про skills пока игнорируй.
5. Запусти `./mr-review start` и убедись, что http://127.0.0.1:8765 отвечает.
Ничего не публикуй наружу и не трогай мои токены: glab и агент уже авторизованы на этой машине.
```

Второй — агенту **в корне вашего проекта**, чтобы завести недостающие skills под ваш стек:

```text
В этом репозитории заведи skills для dashboard mr-review (github.com/arturgilmanov94/gitlab_manager),
контракт — в его docs/SKILLS.md, шаблоны — в docs/DEPLOY.md.
1. Посмотри, что уже есть в .claude/ (agents, commands, skills) и что из этого закрывает ревью MR,
   исследование и решение задач. Ничего не переименовывай.
2. Чего не хватает — создай: .claude/skills/mr-review/SKILL.md, task-plan, task-implement, mr-fix-comments.
   Пиши их под ЭТОТ проект: язык и фреймворк, где лежат тесты, чем запускаются линтеры, правила из CLAUDE.md,
   что в этом проекте считается критичным.
3. Жёсткие рамки для всех: ревью и исследование — только чтение; реализация и исправления — правки только в
   текущем workspace, без commit/push/checkout/reset и без записи в GitLab; ответ — строго JSON по схеме,
   которую передаёт dashboard (свою схему не придумывай).
4. Если уже существующие skills называются иначе — не трогай их, а выпиши мне строки SKILL_* для .env.
5. В конце покажи таблицу: действие dashboard → файл, который его теперь обслуживает.
```

## Проверка, что всё работает

1. `./mr-review doctor` — ни одного FAIL.
2. Откройте `http://127.0.0.1:8765`, вкладка **Merge requests** → «Синхронизировать с GitLab». Должны
   появиться ваши MR (по умолчанию — где вы автор, assignee или reviewer, в текущем проекте).
3. На любом MR — «Запустить ревью». Страница запуска покажет шаги агента в реальном времени; по окончании —
   summary, вердикт и замечания со ссылками на файл и строку в GitLab.
4. Вкладка **Задачи** → «Синхронизировать»: задачи, где вы assignee. «Исследовать» даст план, ничего не меняя.
5. Вкладка **Workspaces** — все git worktree, которые создал dashboard; ваша рабочая копия и текущая ветка
   при этом не трогаются никогда.

Первый запуск на большом проекте небыстрый: агент читает код. Ход видно на странице сессии, запуск можно
отменить кнопкой.

## Обновление и удаление

**Обновление:** остановите сервер, замените бинарник, запустите снова.

```sh
./mr-review stop
tar -xzf mr-review-<new>-linux-amd64.tar.gz     # поверх, либо go build в исходниках
./mr-review start
```

База мигрируется сама при старте; `.env`, история запусков и настройки остаются. Перезапускать лучше, когда
ни один агент не работает: активные запуски прервутся и пометятся упавшими.

**Удаление:** остановите сервер, уберите ярлыки (`./install-desktop.sh --uninstall`, если ставили) и удалите
каталог. Всё своё dashboard держит рядом с бинарником — `data/` (SQLite), `logs/`, `runtime/` (worktree). В вашем проекте он не оставляет ничего, кроме планов, которые вы
сами сохранили кнопкой «Сохранить план в проект» (`.claude/plans/`).

## Если что-то не так

| Симптом | Что делать |
|---|---|
| `Project root FAIL: not resolved` / `Several sibling git repositories` | Пропишите `PROJECT_ROOT=/путь/к/проекту` в `.env`. |
| `GitLab access FAIL` | `glab auth login --hostname <host>` на этой машине; проверьте `glab api user`. |
| `GitLab project FAIL` | У проекта нет origin на GitLab или он нестандартный — задайте `GITLAB_HOST` и `GITLAB_PROJECT`. |
| Агента нет в списке, хотя в терминале он работает | Обновитесь до 0.26.0+, либо укажите полный путь: `CODEX_BIN=/home/me/.nvm/versions/node/v20.20.0/bin/codex`. |
| `… is already served by another mr-review instance` | Уже запущена копия: `./mr-review stop` или `PORT=8766 ./mr-review`. |
| `Skill: … WARN not found` | Ожидаемого файла нет в проекте — см. [шаг 6](#шаг-6--skills-проекта). Это не ошибка: действие работает по `CLAUDE.md`. |
| Ветки задач создаются не от той ветки | `BASE_BRANCH` в `.env` (по умолчанию `develop`). |
| Задач или MR не видно после синхронизации | Проверьте роли (`GITLAB_SYNC_ROLES`), ограничение на текущий проект (`GITLAB_SYNC_ONLY_PROJECT=0`) и список трекеров (`GITLAB_ISSUE_PROJECTS`). Закрытые задачи и влитые MR из списка уходят намеренно. |
| Запуск завис или слишком дорогой | Кнопка «Отменить»; лимиты `RUN_TIMEOUT_SEC` и `CLAUDE_MAX_BUDGET_USD`. |
| Хочу увидеть, что именно получил агент | Страница запуска → «Промпт» и «Полный лог». |
